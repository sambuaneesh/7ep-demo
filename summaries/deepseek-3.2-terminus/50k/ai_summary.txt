# Comprehensive Architectural Summary for Microservice Decomposition Analysis

## SYSTEM OVERVIEW

**Project Name**: Demo (7ep-demo)
**Type**: Multi-module educational web application demonstrating software engineering best practices with comprehensive testing suite
**Primary Technology Stack**: Java, Gradle, Tomcat, H2 Database, Selenium
**Architecture Pattern**: Monolithic web application with server-side rendering and layered architecture

## CORE COMPONENTS & RESPONSIBILITIES

### 1. Authentication Domain (`com.coveros.training.authentication`)

#### Core Components:
- **LoginServlet**: Handles user authentication via POST `/login`
  - Returns: "access granted", "access denied", "no username provided", "no password provided"
  - Uses LoginUtils for credential validation
- **RegisterServlet**: Manages user registration via POST `/register`
  - Returns RegistrationResult with status and message
- **LoginUtils**: Core authentication business logic
  - Method: `isUserRegistered(username, password)` - validates credentials against database
- **RegistrationUtils**: User registration validation and processing
  - Methods: `processRegistration(username, password)`, `isUserInDatabase(username)`
  - Password validation includes entropy calculation and strength checks

#### Domain Objects:
- **User**: `{id: int, name: String}`
- **RegistrationResult**: `{success: boolean, status: RegistrationStatusEnums, message: String}`
- **PasswordResult**: `{status: PasswordResultEnums, entropy: double, timeToCrackOffline: String, timeToCrackOnline: String, message: String}`

#### Status Enums:
- **RegistrationStatusEnums**: SUCCESSFULLY_REGISTERED, EMPTY_USERNAME, BAD_PASSWORD, ALREADY_REGISTERED
- **PasswordResultEnums**: SUCCESS, TOO_SHORT, EMPTY_PASSWORD

### 2. Library Management Domain (`com.coveros.training.library`)

#### Core Components:
- **LibraryUtils**: Central business logic for library operations
  - Methods: `lendBook()`, `registerBook()`, `registerBorrower()`, `searchForBookByTitle()`, `searchForBorrowerByName()`, `listAvailableBooks()`, `deleteBook()`, `deleteBorrower()`
- **LibraryRegisterBookServlet**: Book registration endpoint via POST `/registerbook`
- **LibraryRegisterBorrowerServlet**: Borrower registration endpoint via POST `/registerborrower`
- **LibraryLendServlet**: Book lending operations via POST `/lend`
- **LibraryBookListAvailableServlet**: Lists available books via GET `/listavailable`
- **LibraryBookListSearchServlet**: Book search functionality via GET `/book`
- **LibraryBorrowerListSearchServlet**: Borrower search functionality via GET `/borrower`

#### Domain Objects:
- **Book**: `{id: int, title: String}`
- **Borrower**: `{id: int, name: String}`
- **Loan**: `{book: Book, borrower: Borrower, id: int, borrowDate: Date}`
- **LibraryActionResults**: Enum with SUCCESS, BORROWER_NOT_REGISTERED, BOOK_NOT_REGISTERED, BOOK_CHECKED_OUT

### 3. Mathematics Domain (`com.coveros.training.mathematics`)

#### Core Components:
- **MathServlet**: Basic arithmetic operations via POST `/math`
- **FibServlet**: Fibonacci sequence calculations via POST `/fibonacci`
  - Parameters: `fib_param_n`, `fib_algorithm_choice`
- **AckServlet**: Ackermann function computation via POST `/ackermann`
  - Parameters: `ack_param_m`, `ack_param_n`, `ack_algorithm_choice`
- **Calculator**: Addition operations with validation
- **Fibonacci**: Fibonacci algorithms (recursive/iterative)
  - Regular recursive: `Fibonacci.calculate(n)`
  - Iterative algorithms: `FibonacciIterative.fibAlgo1(n)`, `FibonacciIterative.fibAlgo2(n)`
- **Ackermann**: Ackermann function implementations
  - Regular recursive: `Ackermann.calculate(m, n)`
  - Iterative: `AckermannIterative.calculate(m, n)`
  - Handles large numbers with BigInteger

### 4. Specialized Calculation Modules

#### Expenses Module (`com.coveros.training.expenses`):
- **AlcoholCalculator**: Calculates alcohol-related expenses
- **AlcoholResult**: Expense calculation results
- **DinnerPrices**: Dinner pricing data structure

#### Cartesian Product Module (`com.coveros.training.cartesianproduct`):
- **CartesianProduct**: Computes Cartesian products of sets

#### Auto Insurance Module (`desktop_app`):
- **AutoInsuranceUI**: Swing-based desktop UI
- **AutoInsuranceProcessor**: Auto insurance premium calculation logic
- **AutoInsuranceScriptServer**: Socket server for UI automation (Port 8000)
- **AutoInsuranceAction**: Insurance action result object
- **WarningLetterEnum**: Insurance warning types

### 5. Infrastructure Components

#### Persistence Layer (`com.coveros.training.persistence`):
- **PersistenceLayer**: Database abstraction layer implementing IPersistenceLayer interface
- **IPersistenceLayer**: Persistence interface defining data access operations
- **DbServlet**: Database operations endpoint via GET `/flyway` (database migration/clean operations)
- **ParameterObject**: SQL parameter handling
- **SqlData**: SQL execution wrapper (micro-ORM implementation)

#### Key Persistence Methods:
- `areCredentialsValid(username, password)`
- `searchForUserByName(username)`
- `searchBooksByTitle(title)`, `searchBooksById(id)`
- `searchBorrowerDataByName(name)`
- `createLoan(book, borrower, date)`
- `cleanDatabase()`, `migrateDatabase()`

#### Helper Utilities (`com.coveros.training.helpers`):
- **ServletUtils**: Common servlet operations, JSP paths, request forwarding and response handling
- **StringUtils**: String manipulation utilities, JSON escaping, null handling
- **CheckUtils**: Validation utilities and assertion helpers
- **DateUtils**: Date calculations
- **WebAppListener**: Application lifecycle management

## DATABASE SCHEMAS & DATA MODELS

### Database Technology: H2 Database with Flyway Migration

### Database Configuration:
```properties
jdbc:h2:./build/db/training;AUTO_SERVER=TRUE;MODE=PostgreSQL (file-based)
jdbc:h2:mem:training;MODE=PostgreSQL (in-memory for tests)
```

### Schema Migrations:
- **V1**: Creates person table for authentication
- **V2**: Adds tables for authentication and library systems

### Database Structure:
**Schemas:**
- `ADMINISTRATIVE` - Flyway migration history
- `LIBRARY` - Core library data
- `AUTH` - Authentication data

### Core Tables & Data Models:

#### Authentication Domain:
```sql
AUTH.USER (id SERIAL PRIMARY KEY, name VARCHAR(100), password_hash VARCHAR(100))
```

#### Library Domain:
```sql
LIBRARY.BOOK (id SERIAL PRIMARY KEY, title VARCHAR(100))
LIBRARY.BORROWER (id SERIAL PRIMARY KEY, name VARCHAR(100))  
LIBRARY.LOAN (id SERIAL PRIMARY KEY, book_id INT, borrower_id INT, checkout_date DATE, return_date DATE)
```

### Domain Objects Mapping:
- **User**: Authentication user entity → AUTH.USER table
- **Book**: Library book with title and ID → LIBRARY.BOOK table
- **Borrower**: Library patron entity → LIBRARY.BORROWER table
- **Loan**: Book lending transaction record → LIBRARY.LOAN table
- **AutoInsuranceAction**: Insurance calculation result (in-memory)

## KEY BUSINESS LOGIC & ALGORITHMS

### Authentication Logic:
- Password strength validation using Nbvcxz entropy analysis
  - Minimum 10 characters, maximum 100 characters
  - Entropy calculation and time-to-crack estimation
- SHA-256 password hashing for secure storage
- User registration workflow with duplicate prevention
- Login credential verification with timing attack prevention considerations
- Username uniqueness validation

### Library Management Logic:
- Book/borrower registration with duplicate prevention
- Loan management with availability checking
  - Lending requires both book and borrower to be registered
  - Books must be available (not currently loaned)
- Search functionality for books and borrowers (by id, title, name)
- Cascading deletes for loans when books/borrowers are deleted
- Input validation for empty strings and data integrity

### Mathematical Algorithms:
- **Fibonacci Sequence**: Multiple implementations with performance optimizations
  - Recursive Fibonacci
  - Iterative Fibonacci (O(log(n)) and linear algorithms)
- **Ackermann Function**: Complex recursive function demonstration
  - Recursive Ackermann
  - Tail-recursive Ackermann
  - Iterative implementations with BigInteger for large numbers
- **Input Validation**: Integer bounds checking and overflow prevention
- **Cartesian Product**: Set combination calculations

### Auto Insurance Business Rules:
- Premium calculation based on claims and age
- Warning letter determination
- Policy cancellation conditions
```java
// Example: Young drivers with 1 claim get $100 increase + LTR1 warning
if (claims == 1 && age >= 16 && age <= 25) {
    return new AutoInsuranceAction(100, WarningLetterEnum.LTR1, false, false);
}
```

### Expense Calculation Logic:
- Alcohol expense computations
- Dinner pricing calculations

## MICROSERVICE DECOMPOSITION OPPORTUNITIES

### Potential Service Boundaries:

#### 1. Authentication Service
- **Components**: LoginServlet, RegisterServlet, LoginUtils, RegistrationUtils
- **Data Domain**: User credentials, registration data
- **API**: `/login`, `/register` endpoints
- **Dependencies**: Password hashing, entropy validation, user storage

#### 2. Library Management Service
- **Components**: All LibraryUtils, Library*Servlets, Book/Borrower/Loan domain objects
- **Data Domain**: Books, borrowers, loans
- **API**: `/registerbook`, `/registerborrower`, `/lend`, `/book`, `/borrower`, `/listavailable`
- **Business Logic**: Availability checking, loan validation, search functionality

#### 3. Mathematics & Calculation Service
- **Components**: MathServlet, FibServlet, AckServlet, algorithm implementations
- **Data Domain**: Computational functions (stateless)
- **API**: `/math`, `/fibonacci`, `/ackermann`
- **Specialized Modules**: Cartesian product, expense calculations

#### 4. Insurance Service
- **Components**: AutoInsuranceProcessor, AutoInsuranceScriptServer
- **Data Domain**: Insurance calculations, premium rules
- **Interface**: Socket-based protocol (Port 8000)
- **Business Logic**: Premium calculation, warning letter determination

#### 5. Persistence Service (Optional)
- **Components**: PersistenceLayer, IPersistenceLayer interface
- **Responsibility**: Database abstraction and data access
- **Consideration**: Could be integrated into domain services instead

### Integration & Data Consistency Considerations:

#### Data Domain Isolation:
- Authentication data (users) → Authentication Service
- Library data (books, borrowers, loans) → Library Service
- Insurance calculation data → Insurance Service
- Mathematical functions (stateless) → Mathematics Service

#### Interface Design:
- **RESTful APIs** for web services with JSON payloads
- **Message queues** for asynchronous operations (loan processing, notifications)
- **Socket-based protocols** for real-time communication (insurance desktop integration)
- **Shared domain objects** would require duplication or shared library

#### Data Consistency Challenges:
- Loan creation requires coordinated book/borrower validation across services
- User registration involves password validation and storage coordination
- Book deletion cascades to loan records (cross-service transactions)
- Shared session management for authenticated users

#### Migration Strategy:
- **API Gateway**: Frontend consolidation and routing
- **Service-to-Service Authentication**: Required for inter-service communication
- **Database Per Service**: Pattern for data isolation
- **Gradual Decomposition**: Start with most independent domains (Mathematics, Insurance)

### Technical Implementation Considerations:

#### Service Communication:
- Synchronous REST APIs for immediate responses
- Asynchronous messaging for background processing
- Circuit breakers for fault tolerance
- Service discovery for dynamic routing

#### Data Management:
- Separate databases per service with clear ownership
- Event sourcing for data consistency across boundaries
- API composition for cross-domain queries
- Caching strategies for performance optimization

#### Deployment & Operations:
- Containerization (Docker) for each service
- Centralized logging and monitoring
- CI/CD pipelines per service
- Configuration management for distributed environment

This architecture demonstrates a well-structured monolithic application with clear domain boundaries that align exceptionally well with microservice decomposition. The existing separation of concerns, well-defined API boundaries in the servlet layer, and distinct data domains provide an excellent foundation for transitioning to a microservices architecture.
