# Comprehensive Architectural Summary - 7ep-demo Codebase

## 1. SYSTEM OVERVIEW & BUSINESS DOMAINS

### 1.1 Primary Application
**"7ep-demo"** - A multi-module demonstration application showcasing full-stack software engineering practices with comprehensive testing and CI/CD capabilities. The system follows a monolithic architecture with clear domain separation.

### 1.2 Business Domains
- **Auto Insurance**: Desktop application for insurance premium calculations with Swing UI
- **Authentication**: User registration, login, and credential management system
- **Library Management**: Book/borrower tracking and lending system with inventory management
- **Mathematics**: Computational services (Ackermann, Fibonacci, basic arithmetic operations)
- **Expense Management**: Alcohol expense calculations (testing domain)

## 2. CORE COMPONENTS & RESPONSIBILITIES

### 2.1 Desktop Application Module (`desktop_app/`)
**AutoInsuranceUI** - Swing-based desktop UI for insurance calculations
- **Responsibilities**: User interface rendering, input validation, socket server for automation
- **Dependencies**: Swing framework, custom business logic processors

**AutoInsuranceProcessor** - Core business logic for insurance premium calculations
- **Responsibilities**: Calculate premium increases based on claims and age
- **Key Algorithm**: Rule-based premium calculation with age brackets (16-25, 26-85) and claim tiers

**AutoInsuranceScriptServer** - Socket server for UI automation
- **Responsibilities**: TCP server on port 8000, command processing for UI automation
- **Protocol**: Custom text-based protocol with commands (set, get, click, quit)

### 2.2 Web Application Core (`src/main/java/`)

#### Persistence Layer
- **`PersistenceLayer`** - Main data access layer implementing `IPersistenceLayer` interface
- **`IPersistenceLayer`** - Comprehensive database operations contract
- **`DbServlet`** - Web endpoint for database management operations (clean, migrate)
- **`EmptyDataSource`** - Null object pattern implementation for testing
- **`SqlData`** - SQL operation encapsulation with prepared statement management
- **`ParameterObject`** - Type-safe SQL parameter container
- **`SqlRuntimeException`** - Database operation exception wrapper

#### Authentication Domain
- **`LoginServlet`** & **`RegisterServlet`** - HTTP endpoints for user management
- **`LoginUtils`** & **`RegistrationUtils`** - Business logic for authentication
- **Domain Objects**: `User`, `PasswordResult`, `RegistrationResult`

#### Library Domain
- **`LibraryUtils`** - Core library business logic
- **Servlets**: `LibraryRegisterBookServlet`, `LibraryLendServlet`, `LibraryBookListAvailableServlet`, `LibraryBookListSearchServlet`, `LibraryBorrowerListSearchServlet`, `LibraryRegisterBorrowerServlet`
- **Domain Objects**: `Book`, `Borrower`, `Loan`, `LibraryActionResults`

#### Mathematics Domain
- **`MathServlet`** - Basic arithmetic operations
- **`FibServlet`** & **`AckServlet`** - Specialized mathematical functions
- **`Calculator`** - Basic arithmetic and utility functions
- **`Fibonacci`/`FibonacciIterative`** - Fibonacci implementations (recursive & iterative)
- **`Ackermann`/`AckermannIterative`** - Ackermann function implementations

#### Helper Components
- **`ServletUtils`** - Servlet request/response handling utilities
- **`StringUtils`** - String manipulation and JSON escaping
- **`CheckUtils`** - Validation and assertion utilities
- **`WebAppListener`** - Servlet context listener for database initialization

### 2.3 Frontend Components
- **HTML Pages**: `index.html`, `library.html`, `endpointcatalog.html`, `dbhelp.html`
- **CSS**: `main.css`, `catalog.css` - Responsive styling
- **JavaScript**: `library.js`, `catalog.js` - Client-side functionality including autocomplete, form handling

### 2.4 Testing Infrastructure
**UI Test Server (uitestbox)**
- Selenium-based UI testing with Chrome/Chromedriver
- OWASP ZAP security scanning proxy (port 9888)
- KDE Plasma desktop environment for visual testing
- Python 3.7 + Behave for BDD testing

### 2.5 CI/CD Infrastructure
**Jenkins Server (jenkinsbox)**
- Continuous integration/delivery orchestration
- Pipeline management with multi-stage testing
- Integration with Git repositories via post-receive hooks
- Plugin ecosystem (Sidebar-Link, SonarQube Scanner)

## 4. DATABASE SCHEMAS & DATA MODELS

### 4.1 Database Configuration
- **Framework**: FlywayDB for database migrations
- **Database**: H2 in-memory database (file-based and in-memory modes)
- **Connection**: `jdbc:h2:mem:training;MODE=PostgreSQL;AUTO_SERVER=TRUE`
- **Pooling**: `JdbcConnectionPool` for connection management

### 4.2 Database Schema Structure
- **Schemas**: `ADMINISTRATIVE`, `LIBRARY`, `AUTH`

## 6. KEY BUSINESS LOGIC & ALGORITHMS

### 6.1 Auto Insurance Premium Algorithm
```java
// Rules-based calculation:
// Claims | Age 16-25 | Age 26-85
// 0      | +$50      | +$25
// 1      | +$100     | +$50  
// 2-4    | +$400     | +$200
// >=5    | Cancel     | Cancel
```

### 6.2 Mathematical Algorithms

#### Fibonacci Implementations
- **Recursive**: `Fibonacci.calculate(n)` - Traditional recursive approach
- **Iterative Variant 1**: `FibonacciIterative.fibAlgo1(n)` - Optimized iterative
- **Iterative Variant 2**: `FibonacciIterative.fibAlgo2(n)` - Alternative iterative
- **Performance**: O(log(n)) optimized implementations available

#### Ackermann Function
- **Recursive**: `Ackermann.calculate(m, n)` - Standard recursive implementation
- **Iterative**: `AckermannIterative.calculate(m, n)` - Stack-based iterative
- **Tail-Recursive**: Optimized tail-recursive variant

#### Basic Mathematics
- **Calculator**: Basic arithmetic operations (addition, subtraction, multiplication, division)
- **Cartesian Product**: Set operations (placeholder implementation)

### 6.3 Authentication Logic
- Password strength validation using **Nbvcxz** entropy analysis
- Minimum 10 character password requirement
- Password hashing (SHA-256) before storage
- Credential validation against stored hashes
- User registration workflow with validation

### 6.4 Library Business Rules
- Book availability checking before lending
- Prevention of duplicate registrations (books/borrowers)
- Loan tracking with date management
- Validation of existing entities before operations
- Search functionality (by ID, title, name)

### 6.5 Data Access Patterns
- **Micro-ORM Pattern**: Lightweight object-relational mapping in PersistenceLayer
- **Template Method Pattern**: SQL execution templates

## 10. MICROSERVICE DECOMPOSITION ANALYSIS

### 10.1 Service Boundary Identification

#### Primary Service Candidates
1. **Authentication Service**
   - User management, registration, login
   - Password validation and hashing
   - Session management
   - **Data Domain**: AUTH.USER table

2. **Library Management Service**
   - Book/borrower registration and management
   - Lending operations and availability tracking
   - Search and inventory management
   - **Data Domain**: LIBRARY schema (BOOK, BORROWER, LOAN tables)

3. **Mathematics Service**
   - Computational services (stateless)
   - Fibonacci sequence calculations
   - Ackermann function computations
   - Basic arithmetic operations
   - **Data Domain**: None (stateless)

4. **Insurance Service**
   - Premium calculations and business rules
   - Policy management
   - Currently desktop-based, could be web-enabled
   - **Data Domain**: Insurance-specific data models

5. **Persistence Abstraction Service**
   - Generic data access patterns
   - Database migration management
   - Connection pooling and optimization

#### Infrastructure Services
6. **API Gateway Service**
   - Request routing and composition
   - Rate limiting and security
   - Load balancing

7. **Testing Orchestration Service**
   - Cross-platform test execution
   - Test report aggregation
   - CI/CD pipeline coordination

8. **Monitoring & Reporting Service**
   - Application metrics collection
   - Test result analytics
   - Performance monitoring

### 10.2 Service Characteristics

#### Stateless Services
- **Mathematics Service**: Pure computational, no persistence requirements
- **API Gateway**: Request routing, minimal state

#### Stateful Services
- **Authentication Service**: User credentials and sessions
- **Library Service**: Book inventory, borrower data, loan records
- **Insurance Service**: Policy data and calculation history

#### Infrastructure Services
- **Persistence Service**: Database connections and migrations
- **Testing Service**: Test execution coordination and reporting

### 10.3 Data Domain Boundaries

#### Independent Data Stores
- **Authentication Data**: User credentials, session tokens
- **Library Data**: Books, borrowers, loans - strong internal relationships
- **Insurance Data**: Policies, claims, premium calculations

#### Shared Data Considerations
- User references across services may require unique identifiers
- Loan records might reference both library and user data
- Consolidated reporting may require data aggregation

### 10.4 Integration Patterns

#### Service Communication
- **Synchronous**: RESTful APIs between services
- **Asynchronous**: Message queues for domain events (book lent, user registered)
- **Event-Driven**: Domain events for cross-service notifications

#### Data Consistency
- **Eventual Consistency**: Appropriate for most business domains
- **Saga Pattern**: For complex transactions spanning multiple services
- **CQRS**: Separate read/write models for complex query requirements

#### Cross-Cutting Concerns
- **Centralized Logging**: Structured logging across all services
- **Distributed Tracing**: Request correlation across service boundaries
- **Configuration Management**: Shared configuration service
- **Service Discovery**: Dynamic service location and health checking

### 10.5 Migration Strategy

#### Incremental Decomposition
1. **Extract Mathematics Service** (lowest risk, stateless)
2. **Extract Authentication Service** (clear boundaries)
3. **Extract Library Service** (complex but well-contained)
4. **Refactor Insurance Module** (desktop to web service)
5. **Introduce API Gateway** (request routing and composition)

#### Data Migration Approach
- **Database per Service**: Each service owns its data schema
- **Shared Database Initially**: Gradual schema separation
- **Data Synchronization**: For reference data across services

#### Testing Strategy Evolution
- **Contract Testing**: Service interface validation
- **Consumer-Driven Contracts**: API compatibility assurance
- **Integration Testing**: Service interaction validation
- **End-to-End Testing**: Full workflow verification

This comprehensive architecture provides a solid foundation for microservice decomposition with clear domain boundaries, well-defined interfaces, and comprehensive testing infrastructure. The current monolithic structure demonstrates excellent separation of concerns, making it amenable to incremental decomposition while maintaining system stability and test coverage.
