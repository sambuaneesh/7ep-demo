## Architectural Summary for Microservice Decomposition - Codebase Part 2

### 1. Core Services
#### a. **Authentication Service**
- **Responsibilities**:  
  - User registration validation  
  - Credential authentication  
  - Password complexity enforcement  

- **Endpoints**:  
  - POST `/register` → Registers a new user  
  - POST `/login` → Authenticates a user  

- **Key Components**:  
  - `User` domain object  
  - `RegistrationUtils` (Business logic for password validation and registration)  
  - `LoginUtils` (Credential verification logic)  
  - `RegisterServlet` and `LoginServlet` as API handlers  

#### b. **Library Management Service**
- **Responsibilities**:  
  - Book/borrower registration  
  - Loan processing (checkout, deletion of books/borrowers)  
  - Borrower and book search/list operations  

- **Endpoints**:  
  - POST `/registerbook` → Creates a new book  
  - POST `/registerborrower` → Creates a new borrower  
  - POST `/lend` → Loans a book to a registered borrower  
  - GET `/book?id=` → Book lookup by title or ID  
  - GET `/borrower?id=` → Borrower lookup by name or ID  
  - GET `/listavailable` → Retrieves currently available books  

- **Key Components**:  
  - `LibraryUtils` (Business logic for all operations)  
  - `Book`, `Borrower`, `Loan` domain objects  
  - `LibraryBookListAvailableServlet`, `LibraryBookListSearchServlet`, `LibraryLendServlet`, etc.  

#### c. **Math Calculation Service**
- **Responsibilities**:  
  - Arithmetic (addition of integers)  
  - Fibonacci calculations using recursive/iterative algorithms  
  - Ackermann function execution with recursive/tail-recursive variants  

- **Endpoints**:  
  - POST `/math` → Basic addition of numbers  
  - POST `/fibonacci` → Nth Fibonacci number calculation  
  - POST `/ackermann` → Ackermann function execution  

- **Key Components**:  
  - `Ackermann` (Recursive and TailRecursive implementations)  
  - `Fibonacci` (Recursive/iterative methods)  

---

### 2. **Persistence Layer** (Shared Infrastructure)
- **Role**: Centralized data persistence for library and authentication data  
- **Database Schema**:  
  - Tables created via Flyway migrations (`V1__Create_person_table`, `V2__Rest_of_tables_for_auth_and_library`)  
  - Core tables:  
    - `auth.USER` (id, username, hashed password)  
    - `library.BORROWER` (id, name)  
    - `library.BOOK` (id, title)  
    - `library.LOAN` (id, book_id, borrower_id, borrow_date)  
    - Relationships enforced via foreign keys  

- **Key Components**:  
  - `IPersistenceLayer` (Interface for all database operations)  
  - `PersistenceLayer` (H2-JDBC implementation using Flyway for schema management)  
  - `SqlData` (SQL command abstraction with parametric queries)  
  - `DbServlet` (Exposed for reset/migration operations)  

- **Constraints**:  
  - H2 in-memory database with `MODE=PostgreSQL` compatibility  
  - Default schemas: `ADMINISTRATIVE`, `AUTH`, `LIBRARY`  
  - Uses sequences for auto-incrementing IDs (each entity has separate sequences)  

---

### 3. **Service Dependencies**
- **User Management** (Authentication):  
  - Depends on `PersistenceLayer` for user registration and password storage  
  - Communicates with DB through SQL queries via Flyway  

- **Library Operations**:  
  - Depends on `PersistenceLayer` for borrower, book, and loan operations  
  - Enforces business rules after persistence operations (e.g., checking loan availability)  

- **Math Operations**:  
  - No dependencies on persistence or external services  
  - Uses algorithm-specific logic (Ackermann, Fibonacci) for calculations  

---

### 4. **Communication Patterns**
- **Internal**:  
  - Servlets route API calls to business logic (`LibraryUtils`, `RegistrationUtils`)  
  - Business logic performs validation and delegates to persistence layer  
- **Inter-Service**:  
  - Not directly applicable (monolithic context assumed here)  
  - Future implementation would involve service-to-service API calls (REST or gRPC)  

---

### 5. **Key Algorithms / Business Logic**
- **Password Complexity Check**:  
  - Utilizes **`nbvcxz`** library to calculate entropy of provided passwords  
  - Thresholds: Min 10 characters (too short), Max 100 characters (too long)  

- **Ackermann Function**:  
  - Naive recursive approach (potentially stack-heavy)  
  - Optimized tail-recursive version with a stack implementation using `TailRecursive` interface  
  - Handles large integers via `BigInteger` to avoid overflow  

- **Fibonacci Sequence**:  
  - O(2^n) time recursive algorithm (`Fibonacci.java`)  
  - O(n) logarithmic time algorithm (`FibonacciIterative.java`) using matrix exponentiation  
  - Returns `BigInteger` for high-number calculations

### 8. **Architectural Observations**
- **Servlet Layer Isolation**:  
  - REST API endpoints (`/fibonacci`, `/login`, etc.) encapsulated in servlets  
  - Central HTTP handler (`ServletUtils`) forward responses to appropriate JSP fragments  

- **Business Layer**:  
  - Encapsulated in `Utils` classes (`RegistrationUtils`, `LibraryUtils`)  
  - Uses **Factory Pattern** to provide mock/in-memory versions for testing  

- **Database Abstraction**:  
  - DB operations are centralized in the `IPersistenceLayer` implementation  
  - `PersistenceLayer` abstracts raw SQL via a **Micro ORM** (e.g., `SqlData`)  
  - Migration scripts use **Flyway** for schema management  

- **Input/Output Handling**:  
  - Raw input from HTTP is validated (non-null, correct types)  
  - JSON-escaped output via `StringUtils.escapeForJson()` for user-facing servlets

### 9. **Decomposition Candidates**
#### a. **Authentication Microservice**  
- Endpoints:  
  - **`/register`**, **`/login`**  
- Business Logic Boundary:  
  - User registration and login validation, using Flyway-managed database table  
- DB Schema:  
  - `auth.USER` table  

#### b. **Library Management Microservice**  
- Endpoints:  
  - **`/book`**, **`/borrower`**, **`/lend`**, **`/listavailable`**, **`/registerbook`**, **`/registerborrower`**  
- Business Logic Boundary:  
  - Loan processing, book availability tracking, CRUD operations for books/borrowers  
- DB Schema:  
  - `library.BORROWER`, `library.BOOK`, `library.LOAN` tables  

#### c. **Math Microservice**  
- Endpoints:  
  - **`/math`**, **`/fibonacci`**, **`/ackermann`**  
- Business Logic Boundary:  
  - Mathematical logic that must be tested independently of persistence  
- DB Usage:  
  - No database persistence, input validation only  

#### d. **Persistence Layer** (Could be a shared infrastructure service)  
- Exposes Flyway DB schemas (`/flyway`) for startup  
- Schemas: `AUTH`, `LIBRARY`, `ADMINISTRATIVE`  
- Supports backup/restore as part of integration testing

### 10. **Future Refactoring Opportunities**
- Decouple Flyway usage to a dedicated schema management component  
- Implement authentication-to-library relationships using HTTP (e.g., JWT verification instead of internal logic)  
- Extract logging and error handling into a common helper component  
- Convert shared models like `Book`, `Borrower`, `User` into service-specific models to avoid cross-service coupling  

---

### 11. **Critical Assumptions**
- No cross-service dependencies (simplifies decomposition)  
- Persistence layer is the only source of truth for service data  
- Math components are isolated and have no database impact in their implemented form  
- Password entropy check is a hardcoded policy that could be decoupled
