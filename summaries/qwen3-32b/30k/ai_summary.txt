### **1.2 Web Application**
- **Components**:
  - **Servlets**: 
    - `/math`: REST API for arithmetic operations (e.g., summing inputs).
    - `/ackermann`: REST API for recursive/iterative Ackermann function.
    - `/fibonacci`: REST API for Fibonacci calculations.
    - `/flyway`: DB management endpoint (clean/migrate).
  - **Domain Models**:
    - **Book/Loan/Borrower**: Core data structures for library management.
    - **User**: Data model for authentication.
  - **PersistenceLayer**: Centralized DB access via Flyway, SQL parameterized queries, and H2.
  - **WebAppListener**: Tomcat lifecycle listener to initialize DB on startup.
- **Responsibilities**:
  - Provide multi-tenant, stateless REST services for mathematical and library operations.
  - Maintain data integrity via Flyway-managed H2/PostgreSQL tables.

### **1.3 Testing Infrastructure**
- **Jenkins CI/CD Pipeline**:
  - Orchestrates unit tests, integration tests, Flyway migrations, and deployment to Tomcat.
  - Integrates OWASP ZAP, JMeter (performance), and DependencyCheck for security testing.
- **Unit/Integration Tests**:
  - JUnit-based tests for core logic (e.g., `MathServletTests`, `AckermannParameterizedTests`).
  - Mocked `PersistenceLayer` and `EmptyDataSource` for test isolation.
- **UI Tests**:
  - Selenium (Java/JS/C#): End-to-end tests for book/borrower/loan workflows.
  - Behave (Python): BDD tests for library management and math operations.
  - Page Object Model (POM): Encapsulates UI interactions for maintainability.

## **8. Microservice Decomposition Opportunities**

### **8.1 Candidate Microservices**
| Microservice                    | Components Involved                                               | Key Responsibilities                              | Data Ownership                              |
|---------------------------------|--------------------------------------------------------------------|---------------------------------------------------|---------------------------------------------|
| **Mathematical Functions**       | `Ackermann`, `Fibonacci`, `MathServlet`                            | REST services for recursive/iterative algorithms.  | None (stateless compute).                     |
| **Library Management**           | `Book`, `Borrower`, `Loan`, `Library*Servlet`                      | Book registration, lending/return, and search.     | Owns `Books`, `Loans`, and `Borrowers` tables. |
| **User Authentication**          | `User`, `RegistrationUtils`, `LoginServlet`                        | Secure user registration and password policy enforcement. | Owns `Users` table.                              |
| **Database Management**           | `DbServlet`, `WebAppListener`, `Flyway Migrations`                 | Schema initialization, resets, and versioning.     | Manages Flyway history and DB schema.        |
| **UI Testing Service**            | Selenium/Behave tests, Page Objects                                | Centralized testing framework for loan workflows.  | None (test framework).                       |

### **8.2 Key Decomposition Challenges**
- **Database Coupling**:
  - Current schema is tightly bound to a monolithic Flyway lifecycle. Decomposition would require distributed data management (e.g., Kafka events or API-driven synchronization).
- **UI Tests Complexity**:
  - Selenium tests are tightly coupled to servlets and JSP UI. Transitioning to API tests would reduce redundancy when services are decomposed.
- **Auth/Perm Model**:
  - Password validation logic is intertwined with `User` entity and `IPersistenceLayer`. Extraction would require shared authentication microservice or JWT-based access.

## **9. Critical Interdependences**

1. **Library ↔ User**:
   - Borrowers must exist before books can be lent (enforced via `PersistenceLayer.validateBorrower()` logic).
2. **UI Tests ↔ Servlets**:
   - Selenium tests assume specific JSP rendering and servlet-based input controls (e.g., autocomplete for borrowers).
3. **WebAppListener ↔ Database**:
   - `WebAppListener` triggers DB reset on startup, creating tight coupling between app lifecycle and data state.

## **10. Decomposition Recommendations**

### **10.1 Service Boundaries**
- **Mathematical Service**: 
  - REST-based, stateless with versioned APIs for Ackermann/Fibonacci. 
  - Use serverless functions (e.g., AWS Lambda) for cost efficiency.
- **Library Service**: 
  - REST-based with CRUD APIs for books and library state tracking. 
  - Implement Kafka for real-time loan updates.
- **Authentication Service**: 
  - Centralized microservice with rate-limited endpoints and password policy enforcement. 
  - Use JWT for cross-service authentication.

### **10.2 Data Architecture**
- **Database per Service**: 
  - Separate `library_db` and `user_db` with Flyway- or Liquibase-managed schemas.
  - Use event sourcing for loan history if needed.
- **Schema Synchronization**: 
  - Employ event-driven pattern (e.g., Kafka) to maintain consistency between services for shared entities (e.g., borrower IDs used in loans).

### **10.3 Test Strategy for Microservices**
- **API Tests**: 
  - Replace Selenium/Behave with REST clients (e.g., Postman, `requests`) for end-to-end validation.
- **Docker Compose**:
  - Use multi-container setup for each service and test suite (e.g., library_db + library_api + test_api).
- **Centralized Security Testing**:
  - Integrate OWASP ZAP as a shared environment for security scans across microservices.
