## Architectural Summary: Coveros Demo Application (Part 1)

### High-Level Architecture
- **Technology Stack**: Java 11, Tomcat 9, H2 Database, Flyway (DB migrations), Gradle build system
- **Deployment**: WAR file deployment to Tomcat with CI/CD via Jenkins
- **Architecture Pattern**: Monolithic web application with clear domain separation, designed for educational purposes to demonstrate software quality practices

### Core Components & Domains

#### 1. **Authentication Service**
- **Responsibilities**: User registration, login validation, password policy enforcement
- **Key Classes**:
  - `LoginServlet` & `RegisterServlet`: HTTP endpoints for authentication
  - `RegistrationUtils`: Password validation, user registration logic
  - `LoginUtils`: Authentication verification
  - `User` domain object: Immutable user representation
  - `RegistrationResult` & `PasswordResult`: Result objects with status enums
- **APIs**:
  - `POST /login`: User authentication
  - `POST /register`: New user registration
- **Business Logic**:
  - Password entropy validation (12+ chars, complexity requirements)
  - Duplicate username detection
  - Session management via servlet context

#### 2. **Library Service**
- **Responsibilities**: Book/borrower management, loan tracking, catalog operations
- **Key Classes**:
  - `LibraryRegisterBookServlet` & `LibraryRegisterBorrowerServlet`: Registration endpoints
  - `LibraryLendServlet`: Book checkout logic
  - `LibraryBookListAvailableServlet` & `LibraryBookListSearchServlet`: Book catalog
  - `LibraryUtils`: Core business logic
  - Domain objects: `Book`, `Borrower`, `Loan` (all immutable)
- **APIs**:
  - `POST /registerbook`: Book registration
  - `POST /registerborrower`: Borrower registration
  - `POST /lend`: Book checkout
  - `GET /library/book/list`: Book catalog
- **Business Logic**:
  - Book availability checking before loan
  - Loan date tracking (SQL Date)
  - Search by title/ID for books/borrowers

#### 3. **Mathematics Service**
- **Responsibilities**: Mathematical computations (addition, Fibonacci, Ackermann)
- **Key Classes**:
  - `MathServlet`, `FibServlet`, `AckServlet`: HTTP endpoints
  - `Calculator`: Core math operations
  - `Fibonacci` & `Ackermann`: Algorithm implementations
- **APIs**:
  - `POST /math`: Integer addition (input validation)
  - `POST /fibonacci`: Fibonacci sequence
  - `POST /ackermann`: Ackermann function
- **Algorithms**:
  - Recursive and iterative implementations
  - Input boundary validation (32-bit integer limits)

#### 4. **Persistence Layer**
- **Responsibilities**: Database abstraction, transaction management
- **Key Classes**:
  - `PersistenceLayer`: Implements `IPersistenceLayer`
  - `ParameterObject`: SQL parameter binding
  - `SqlData`: Result set processing
- **Database**: H2 (in-memory for tests, file-based in prod)
- **Migrations**:
  - `V1__Create_person_table.sql`
  - `V2__Rest_of_tables_for_auth_and_library.sql`

#### 5. **Desktop Application Module**
- **Responsibilities**: Auto insurance premium calculation, UI automation
- **Key Classes**:
  - `AutoInsuranceUI`: Swing-based UI
  - `AutoInsuranceProcessor`: Premium calculation logic
  - `AutoInsuranceScriptServer`: Socket-based automation (port 8000)
  - `AutoInsuranceAction`: Result object with premium increase/warning letters
- **Business Rules**:
  - Age/claim-based premium calculation matrix
  - Policy cancellation for 5+ claims
  - Warning letter triggers (LTR1-3)

### Data Models & Database Schema
1. **Users Table**:
   - `id` (PK), `username`, `password` (hashed), `created_at`
2. **Books Table**:
   - `id` (PK), `title`, `created_at`
3. **Borrowers Table**:
   - `id` (PK), `name`, `created_at`
4. **Loans Table**:
   - `id` (PK), `book_id` (FK), `borrower_id` (FK), `checkout_date`

### API Endpoints Summary
| Endpoint | Method | Purpose | Key Params |
|----------|---------|---------|------------|
| `/login` | POST | User auth | username, password |
| `/register` | POST | User reg | username, password |
| `/math` | POST | Math add | item_a, item_b |
| `/fibonacci` | POST | Fibonacci | n |
| `/registerbook` | POST | Add book | book |
| `/lend` | POST | Loan book | book, borrower |

### Testing Architecture
1. **Unit Tests** (JUnit 5):
   - Located in `src/test/java`
   - Mockito for mocking
   - JaCoCo for coverage
2. **BDD Tests** (Cucumber/Behave):
   - Feature files in `src/bdd_test/resources`
   - Step definitions in `java/com/coveros/training/*`
3. **API Tests** (Python/pytest):
   - `requests` library for HTTP calls
   - Database reset utilities
4. **UI Tests** (Selenium):
   - Cross-language support (Python, Java, JS)
   - Grid support for parallel execution

### CI/CD Pipeline (Jenkins)
- **Stages**:
  1. Build → Unit Tests → BDD Tests
  2. Static Analysis (SonarQube) → Security Scans (OWASP)
  3. Deploy to Test → API/UI Tests
  4. Performance Tests (JMeter) → Mutation Tests (PITest)
- **Quality Gates**:
  - SonarQube coverage threshold
  - OWASP vulnerability checks
  - JMeter performance baselines

### Configuration & Deployment
- **Database Config**: 
  - JDBC URL configurable (`jdbc:h2:mem:training`)
  - Flyway migrations on startup
- **Logging**: Log4j2 XML configuration
- **Build Tools**:
  - Gradle wrapper scripts for cross-platform builds
  - Gretty plugin for hot-reload during dev
- **Environment Settings**:
  - `gradle.properties`: JVM tuning, chromedriver paths
  - Separate configs for test/prod

### Microservice Decomposition Candidates
1. **Authentication Service**:
   - Bounded context: Identity management
   - Interfaces: Registration, login, password policies
2. **Library Service**:
   - Bounded context: Book lending lifecycle
   - Interfaces: Catalog, checkout, search
3. **Mathematics Service**:
   - Bounded context: Computations
   - Interfaces: Calculation APIs with validation
4. **Desktop Automation Service**:
   - Bounded context: UI automation
   - Interfaces: Socket server, calculation engine
5. **Shared Services**:
   - Persistence abstraction
   - Common utilities (validation, error handling)

### Critical Dependencies
- **Database**: H2 (migratable to PostgreSQL)
- **Web Server**: Tomcat 9 (containerizable)
- **Security**: OWASP DependencyCheck, Tomcat SSL
- **Testing**: Selenium WebDriver, Cucumber JVM
- **Build**: Gradle 7.0, Java 11

This architecture provides clear domain boundaries suitable for microservice extraction, with well-defined APIs and testable interfaces. The persistence layer is abstracted to facilitate database changes, and all services are stateless except for the database interactions.

## Comprehensive Architectural Summary (Codebase Chunk 2/3)

### 1. **Core Component Overview**

#### **Authentication Service**
- **Responsibilities**: User registration, login, password validation
- **Key Classes**:
  - `RegisterServlet`: Handles POST `/register` endpoint
  - `LoginServlet`: Handles POST `/login` endpoint
  - `RegistrationUtils`: Business logic for user registration (password entropy validation via Nbvcxz)
  - `LoginUtils`: Credential validation
- **Domain Objects**: `User`, `RegistrationResult`, `PasswordResult`
- **Features**: Password strength checks, duplicate username prevention

#### **Library Management Service**
- **Responsibilities**: Book/borrower CRUD, loan management
- **Key Classes**:
  - `LibraryRegisterBookServlet`: POST `/registerbook`
  - `LibraryRegisterBorrowerServlet`: POST `/registerborrower`
  - `LibraryLendServlet`: POST `/lend`
  - `LibraryBookListSearchServlet`: GET `/book`
  - `LibraryBorrowerListSearchServlet`: GET `/borrower`
  - `LibraryBookListAvailableServlet`: GET `/listavailable`
  - `LibraryUtils`: Core business logic
- **Domain Objects**: `Book`, `Borrower`, `Loan`, `LibraryActionResults`
- **Features**: Book lending/borrowing, availability tracking

#### **Mathematical Service**
- **Responsibilities**: Mathematical calculations (addition, Fibonacci, Ackermann)
- **Key Classes**:
  - `MathServlet`: POST `/math`
  - `FibServlet`: POST `/fibonacci`
  - `AckServlet`: POST `/ackermann`
  - `Calculator`: Basic arithmetic utilities
  - `Fibonacci`/`FibonacciIterative`: Recursive/iterative Fibonacci
  - `Ackermann`/`AckermannIterative`: Recursive/iterative Ackermann
- **Features**: Algorithm selection (recursive vs. tail-recursive)

#### **Persistence Layer**
- **Responsibilities**: Database abstraction, transaction management
- **Key Classes**:
  - `PersistenceLayer`: Implements `IPersistenceLayer`
  - `SqlData`: Micro-ORM for query execution
  - `ParameterObject`: Type-safe SQL parameters
- **Features**: Connection pooling (H2), Flyway migrations, backup/restore

#### **Web Infrastructure**
- **Responsibilities**: HTTP request handling, view rendering
- **Key Classes**:
  - `ServletUtils`: Request forwarding utilities
  - `WebAppListener`: Startup/shutdown hooks
  - JSPs (`result.jsp`, `restfulresult.jsp`): Response rendering
- **Frontend**: HTML/CSS/JS for library UI

---

### 2. **Database Schema (via Flyway Migrations)**
```sql
-- Authentication Schema (AUTH)
USER (
  id SERIAL PRIMARY KEY,
  name VARCHAR(100) NOT NULL,
  password_hash VARCHAR(100)
)

-- Library Schema (LIBRARY)
BOOK (
  id SERIAL PRIMARY KEY,
  title VARCHAR(100) NOT NULL
)

BORROWER (
  id SERIAL PRIMARY KEY,
  name VARCHAR(100) NOT NULL
)

LOAN (
  id SERIAL PRIMARY KEY,
  book INT REFERENCES BOOK(id) ON DELETE CASCADE,
  borrower INT REFERENCES BORROWER(id) ON DELETE CASCADE,
  borrow_date DATE NOT NULL
)
```

### 3. **API Endpoints**
| **Endpoint** | **Method** | **Responsibility** | **Input** | **Output** |
|--------------|------------|-------------------|-----------|------------|
| `/register` | POST | User registration | username, password | `RegistrationResult` |
| `/login` | POST | User authentication | username, password | "access granted/denied" |

---

### 4. **Service Dependencies**
- **All services** → `PersistenceLayer` (database access)
- **Authentication** → Nbvcxz (password entropy)
- **Math services** → No external deps (pure algorithms)
- **Library** → `PersistenceLayer` (CRUD + loan logic)
- **Web layer** → Business utils (LibraryUtils, LoginUtils, etc.)

---

### 5. **Key Business Logic**
- **Password Validation**:
  - Min 10 chars, max 100 chars
  - Entropy check via `Nbvcxz.estimate()`
  - Time-to-crack calculations
- **Book Lending**:
  - Validate book/borrower existence
  - Check availability via `searchForLoanByBook()`
  - Create `Loan` record with date
- **Math Algorithms**:
  - Recursive vs. tail-recursive implementations
  - BigInteger for large numbers (Ackermann)
- **Pagination/Search**:
  - Book/borrower listing with "available" filtering
  - Search by ID (exact) or title/name (contains)

---

### 6. **Configuration & Deployment**
- **Database**: H2 in-memory (for tests), file-based (`./build/db/training`)
- **Server**: Apache Tomcat (via servlets)
- **Migrations**: Flyway-managed (versions V1, V2)
- **Logging**: Log4j2 (INFO level, console output)
- **Frontend**: Plain HTML/CSS/JS (no frameworks)
- **Testing**: Cucumber (BDD), JUnit (unit/integration), Selenified (UI)

---

### 7. **Architectural Patterns**
- **Layered Architecture**: 
  - Presentation (Servlets/JSP)
  - Business (Utils)
  - Persistence (PersistenceLayer)
- **Domain-Driven Design**: 
  - Explicit domain objects (`Book`, `User`, etc.)
  - Value objects (`LibraryActionResults`)
- **Micro-ORM**: Custom `SqlData` for query parameterization
- **Service Locator**: Static utils (`RegistrationUtils`, `LibraryUtils`)
- **Dependency Injection**: Limited (constructor injection in PersistenceLayer)

---

### 8. **Critical Coupling Points**
1. **Shared Persistence**:
   - All services use `PersistenceLayer`
   - Tight schema coupling (e.g., LOAN references BOOK/BORROWER)
2. **Monolithic Web Layer**:
   - All endpoints in same servlet context
   - Shared `ServletUtils` for response handling
3. **Authentication Cross-Cutting**:
   - User table tied to library operations (e.g., librarian actions)

### 9. **Potential Service Boundaries**
| **Service** | **Domain** | **Database** |
|--------------|------------|--------------|
| Auth Service | Users, passwords | AUTH.USER |
| Catalog Service | Books, borrowers | LIBRARY.BOOK, LIBRARY.BORROWER |
| Lending Service | Loans, availability | LIBRARY.LOAN |
| Math Service | Algorithms | (None - stateless) |
| API Gateway | HTTP routing | (None - facade) |

### 10. **Decomposition Considerations**
- **Data Ownership**: Each microservice should own its DB schema
- **Eventual Consistency**: Loan service needs to sync Book/Borrower status
- **Auth Boundaries**: Library actions require auth token validation
- **Stateless Math**: Pure compute service (no DB needed)
- **API Contract**: OpenAPI specs for inter-service calls

### Comprehensive Architectural Summary for Microservice Decomposition

---

#### **1. Authentication Service**
- **Responsibilities**: User registration, login, credential validation, password strength validation
- **Core Components**:
  - `LoginServlet`: Handles HTTP POST requests for login (`/login`)
  - `RegisterServlet`: Handles user registration (`/register`)
  - `LoginUtils`: Validates user credentials via `IPersistenceLayer`
  - `RegistrationUtils`: Processes registration with password entropy checks
- **API Endpoints**:
  - `POST /login` (username/password)
  - `POST /register` (username/password)
- **Business Logic**:
  - Password entropy validation (minimum length, complexity)
  - User existence checks before registration
  - Session management via servlet attributes
- **Data Models**:
  - `User` (id, username)
  - `PasswordResult` (entropy, time-to-crack metrics)
  - `RegistrationResult` (status, messages)
- **Dependencies**:
  - Persists data via `IPersistenceLayer`
  - Communicates with frontend via JSP (`ServletUtils.RESULT_JSP`)

---

#### **2. Library Management Service**
- **Responsibilities**: Book/borrower registration, lending management, inventory tracking
- **Core Components**:
  - `LibraryLendServlet`: Book lending logic (`/lendbook`)
  - `LibraryRegisterBookServlet`: Book registration (`/registerbook`)
  - `LibraryRegisterBorrowerServlet`: Borrower registration (`/registerborrower`)
  - `LibraryUtils`: Business logic for lending/registration
- **API Endpoints**:
  - `POST /lendbook` (book title, borrower name, date)
  - `POST /registerbook` (book title)
  - `POST /registerborrower` (borrower name)
- **Business Logic**:
  - Validates book/borrower existence before lending
  - Prevents duplicate lending of checked-out books
  - Catalog management (list/search books/borrowers)
- **Data Models**:
  - `Book` (id, title)
  - `Borrower` (id, name)
  - `Loan` (book, borrower, date, id)
- **Dependencies**:
  - Persists data via `IPersistenceLayer`
  - Uses `LibraryActionResults` for status responses

---

#### **3. Mathematics Service**
- **Responsibilities**: Algorithm computations (Fibonacci, Ackermann)
- **Core Components**:
  - `FibServlet`: Fibonacci calculations (`/fib`)
  - `AckServlet`: Ackermann computations (`/ack`)
- **API Endpoints**:
  - `POST /fib` (algorithm choice, input `n`)
  - `POST /ack` (algorithm choice, inputs `m`, `n`)
- **Business Logic**:
  - Supports recursive/iterative algorithms
  - Handles large numbers with `BigInteger`
- **Dependencies**: Stateless; no external data dependencies

---

#### **4. Persistence Layer**
- **Responsibilities**: Database abstraction, migrations, CRUD operations
- **Core Components**:
  - `IPersistenceLayer`: Interface for DB operations
  - `DbServlet`: Database management (`/flyway`)
  - `SqlData`: Parameterized SQL execution
- **API Endpoints**:
  - `GET /flyway?action=clean|migrate`
- **Data Models**:
  - `ParameterObject` (data, type)
  - Domain objects (`User`, `Book`, etc.)
- **Configuration**:
  - Flyway-managed migrations
  - `EmptyDataSource` for test isolation

---

#### **5. Shared Utilities**
- **Responsibilities**: Common operations, validation, string manipulation
- **Core Components**:
  - `StringUtils`: Null handling, JSON escaping
  - `CheckUtils`: Input validation (e.g., positive integers)
  - `DateUtils`: Date operations
- **Key Logic**:
  - String sanitization for JSON safety
  - Input validation with clear error messages

---

#### **6. Frontend Integration**
- **Architecture**: Servlet-based MVC with JSP rendering
- **Endpoints**: RESTful JSON responses via `ServletUtils.RESTFUL_RESULT_JSP`
- **UI Testing Frameworks**:
  - **Behavior-Driven**: Behave (Python) with feature files
  - **E2E Tests**: Selenium (Java/JS/C#/Python)
  - **Page Object Models**: For maintainable UI interactions
- **Key Workflows**:
  - User registration/login
  - Book lending lifecycle
  - Algorithm computations

---

#### **7. Deployment & Configuration**
- **Container**: Apache Tomcat
- **Lifecycle Management**:
  - `WebAppListener`: Initializes/cleans DB on startup
  - Flyway migrations executed via `DbServlet`
- **Logging**: SLF4J with error handling in servlets
- **Test Isolation**: Mocked `IPersistenceLayer` and servlets

---

#### **8. Communication Patterns**
- **Synchronous**: HTTP request/response via servlets
- **Data Transfer**: JSON for UI, Java objects internally
- **Error Handling**: Structured responses with status codes

---

#### **Key Microservice Decomposition Insights**
1. **Bounded Contexts**:
   - Authentication (user identity/security)
   - Library (domain-specific lending logic)
   - Mathematics (stateless computations)
   - Persistence (data abstraction)

2. **Data Ownership**:
   - Each service owns its domain models
   - Shared persistence layer could be split per-service

3. **API Contracts**:
   - RESTful HTTP endpoints with clear input/output schemas
   - Async operations (e.g., migrations) via GET actions

4. **Scalability**:
   - Mathematics service: Highly scalable (stateless)
   - Library service: May need sharding for large inventories
   - Authentication: Cacheable sessions

5. **Testing Strategy**:
   - Unit tests with mocked dependencies
   - Multi-language E2E tests for UI workflows
   - Behavioral tests (Behave) for user journeys

---

### Recommended Microservice Split
1. **Auth Service**  
   `LoginServlet`, `RegisterServlet`, `LoginUtils`, `RegistrationUtils`
2. **Library Service**  
   `LibraryUtils`, all library-related servlets
3. **Math Service**  
   `FibServlet`, `AckServlet`, algorithm classes
4. **Persistence Service**  
   `IPersistenceLayer` implementations, `DbServlet`
5. **Shared Library**  
   Utility classes, domain objects

This decomposition ensures loose coupling, domain-specific scaling, and independent deployment capabilities.
