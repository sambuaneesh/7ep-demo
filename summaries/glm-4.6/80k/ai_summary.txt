
# Comprehensive Architectural Summary: 7ep-demo Codebase

## 1. Overall Architecture

### Technology Stack
- **Language**: Java 11
- **Web Framework**: Servlet-based (Tomcat 9)
- **Build Tool**: Gradle 7.0 with wrapper scripts
- **Database**: H2 (in-memory and file-based modes with PostgreSQL compatibility)
- **Database Migration**: FlywayDB
- **Testing**: 
  - Unit: JUnit 5, Mockito, JaCoCo coverage
  - Integration: File-based H2 tests
  - BDD: Cucumber (Java), Behave (Python)
  - UI: Selenium (Java, Python, JavaScript, C#)
  - Performance: JMeter
  - API: pytest (Python)
- **Static Analysis**: SonarQube
- **Security**: OWASP DependencyCheck, OWASP ZAP proxy (port 8888)
- **CI/CD**: Jenkins with comprehensive pipeline
- **Logging**: Log4j2
- **Desktop UI**: Swing with socket automation
- **Frontend**: HTML/CSS/JavaScript with AJAX communication

### Architectural Patterns
- **Layered Architecture**: Clear separation between presentation (servlets), business logic (Utils classes), and persistence
- **Domain-Driven Design**: Packages organized by business domain (authentication, library, mathematics)
- **MVC Pattern**: 
  - Controllers: Servlets
  - Models: Domain objects
  - Views: JSP/HTML pages
- **Data Access Object (DAO)**: PersistenceLayer implements DAO pattern with IPersistenceLayer interface
- **Front Controller Pattern**: Servlets act as front controllers for endpoints
- **Null Object Pattern**: EmptyDataSource and empty domain objects
- **Template Method Pattern**: PersistenceLayer uses templates for CRUD operations
- **Micro ORM**: SqlData and ParameterObject provide lightweight ORM
- **Immutability**: Domain objects designed as immutable value objects
- **Null Avoidance**: Systematic use of empty objects instead of null values

## 2. Component Overview & Service Dependencies

### Core Components

#### Mathematical Services
- `Calculator`: Utility class for basic arithmetic with overflow checking
- `Fibonacci`: Recursive Fibonacci calculation (exponential time)
- `FibonacciIterative`: Optimized Fibonacci implementations
  - O(log n) using matrix exponentiation
  - O(n) using dynamic programming
- `Ackermann`: Recursive Ackermann function implementation
- `AckermannIterative`: Tail-recursive optimization using functional interfaces
- `FunctionalField`: Generic functional interface for enum-based field access
- `TailRecursive`: Generic tail recursion utility
- `CartesianProduct`: Utility for generating test case combinations
- `AlcoholCalculator`: Restaurant bill splitting (food vs alcohol portions)

#### Library Management
- `LibraryUtils`: Core business logic for book/borrower operations
- `LibraryLendServlet`: Book lending endpoint
- `LibraryRegisterBookServlet`: Book registration endpoint
- `LibraryRegisterBorrowerServlet`: Borrower registration endpoint
- `LibraryBookListSearchServlet`: Book search/listing endpoint
- `LibraryBookListAvailableServlet`: Available books endpoint
- `LibraryBorrowerListSearchServlet`: Borrower search/listing endpoint

#### Authentication
- `LoginServlet`: User authentication endpoint
- `RegisterServlet`: User registration endpoint
- `LoginUtils`: Authentication business logic
- `RegistrationUtils`: Registration business logic with password validation

#### Persistence Layer
- `PersistenceLayer`: Main database interaction class implementing CRUD operations
- `IPersistenceLayer`: Interface defining persistence contracts
- `SqlData`: Micro-ORM for SQL operations
- `ParameterObject`: Type-safe parameter container
- `EmptyDataSource`: Null object for DataSource
- `DbServlet`: Database management endpoint

#### Desktop Application
- `AutoInsuranceProcessor`: Premium calculation based on claims and age
- `AutoInsuranceScriptServer`: Socket server (port 8000) for UI automation
- `AutoInsuranceScriptClient`: Script client for UI automation

### Service Dependencies
```
Servlets → Utils → PersistenceLayer → Database
```

#### Specific Dependencies
- `MathServlet` → `Calculator`
- `FibServlet` → `Fibonacci`/`FibonacciIterative`
- `AckServlet` → `Ackermann`/`AckermannIterative`
- `LibraryLendServlet` → `LibraryUtils` → `IPersistenceLayer`
- `LoginServlet` → `LoginUtils` → `IPersistenceLayer`
- `RegisterServlet` → `RegistrationUtils` → `IPersistenceLayer`
- `RegistrationUtils` → IPersistenceLayer, Nbvcxz library
- `LoginUtils` → IPersistenceLayer
- `LibraryUtils` → IPersistenceLayer

## 3. API Endpoints

### Mathematical APIs
- `POST /math`
  - Parameters: item_a, item_b (integers)
  - Returns: sum result or error message
  - Validates integer inputs, checks for overflow (max: 2,147,483,647)

- `POST /fibonacci`
  - Parameters: fib_param_n (integer), fib_algorithm_choice
  - Returns: nth Fibonacci number

- `POST /ackermann`
  - Parameters: ack_param_m, ack_param_n, algorithm (regular/tail_recursive)
  - Returns: Ackermann function result

### Library APIs
- `POST /lend`
  - Parameters: book (title), borrower (name)
  - Returns: SUCCESS/BOOK_CHECKED_OUT/BOOK_NOT_REGISTERED/BORROWER_NOT_REGISTERED

- `POST /registerbook`
  - Parameters: book title
  - Returns: SUCCESS/ALREADY_REGISTERED_BOOK

- `POST /registerborrower`
  - Parameters: borrower name
  - Returns: SUCCESS/ALREADY_REGISTERED_BORROWER

- `GET /book`
  - Parameters: id (optional), title (optional)
  - Returns: JSON array of books or search results

- `GET /listavailable`
  - Returns: JSON array of available books only

- `GET /borrower`
  - Parameters: id (optional), name (optional)
  - Returns: JSON array of borrowers or search results

### Authentication APIs
- `POST /login`
  - Parameters: username, password
  - Returns: access granted/denied status

- `POST /register`
  - Parameters: username, password
  - Returns: registration status, validation messages, password strength metrics

### Database Management API
- `GET /flyway`
  - Parameters: action (clean/migrate)
  - Returns: migration status

## 4. Database Schema & Persistence

### Database Configuration
- **Type**: H2 with PostgreSQL compatibility mode
- **In-memory URL**: `jdbc:h2:mem:training;MODE=PostgreSQL`
- **File URL**: `jdbc:h2:./build/db/training`
- **Connection Pool**: H2 JdbcConnectionPool
- **Console**: Web-based H2 console at `/console`
- **Migration**: Flyway scripts in `src/main/resources/db/migration`

### Tables & Schema

#### AUTH Schema
- `AUTH.USER`
  - Columns: ID (BIGINT), NAME (VARCHAR), PASSWORD_HASH (VARCHAR)

#### LIBRARY Schema
- `LIBRARY.BOOK`
  - Columns: ID (BIGINT), TITLE (VARCHAR NOT NULL)

- `LIBRARY.BORROWER`
  - Columns: ID (BIGINT), NAME (VARCHAR NOT NULL)

- `LIBRARY.LOAN`
  - Columns: ID (BIGINT), BOOK (BIGINT FK), BORROWER (BIGINT FK), BORROW_DATE (DATE NOT NULL)

#### Administrative Schema
- `ADMINISTRATIVE.FLYWAY_SCHEMA_HISTORY`
  - Flyway migration tracking table

### Relationships
- One-to-many: Book → Loans (a book can have multiple loans over time)
- One-to-many: Borrower → Loans (a borrower can have multiple active loans)
- One-to-many: User → (no direct relationship in schema)

### Migration Scripts
- `V1__Create_person_table.sql`
- `V2__Rest_of_tables_for_auth_and_library.sql`

## 5. Business Logic

### Authentication Business Logic
- **User Registration Workflow**:
  - Duplicate user checking
  - Password strength validation using Nbvcxz entropy calculation
  - Password hashing and storage (SHA-256)
  - Returns RegistrationResult with status, message, and security metrics

- **User Authentication**:
  - Credential validation against stored hashes
  - Session management indicators
  - PasswordResult with entropy and time-to-crack calculations

### Library Business Logic
- **Book Management**:
  - Registration with duplicate checking
  - Availability validation for loans
  - Search by ID/title with flexible matching

- **Borrower Management**:
  - Registration with duplicate checking
  - Search by ID/name

- **Loan Processing**:
  - Book availability checks
  - Transaction boundaries
  - Date tracking for borrowed items

### Mathematics Business Logic
- **Calculator**:
  - Safe integer addition with overflow checks
  - Maximum value: 2,147,483,647 (32-bit signed)

- **Fibonacci Implementations**:
  - Simple recursive (exponential time)
  - Matrix exponentiation (O(log n))
  - Dynamic programming (O(n))

- **Ackermann Function**:
  - Standard recursive implementation
  - Tail-recursive optimization with functional interfaces

### Desktop Application Logic
- **AutoInsuranceProcessor**:
  - Premium calculation based on claims history and age
  - Warning letter determination logic (LTR1, LTR2, LTR3)
  - Policy cancellation rules
  - Returns AutoInsuranceAction with all outcomes

## 10. Key Technical Considerations

### Thread Safety
- Servlets are not thread-safe
- Shared resources use synchronized blocks
- Connection pooling for database access

### Session Management
- Cookie-based tracking only
- Stateless design preferred (Math APIs as examples)
- Auth APIs maintain minimal state

### Performance Considerations
- Multiple Fibonacci algorithms for performance comparison
- Overflow protection in Calculator
- Tail recursion optimization for Ackermann
- Database connection pooling

### Security Measures
- SQL injection protection via prepared statements
- Password strength validation with entropy calculation
- SHA-256 password hashing
- OWASP security scanning integration

### Error Handling
- Custom exceptions with clear error messages
- Consistent error response formats
- Graceful degradation for invalid inputs

## 11. Architectural Considerations for Microservice Decomposition

### Bounded Contexts Identified
1. **Authentication Service**: User registration, login, password validation
2. **Library Service**: Book management, borrower management, lending operations
3. **Mathematics Service**: Calculator, Fibonacci, Ackermann computations
4. **Persistence Service**: Database operations, migrations, connection management
5. **Insurance Service**: Desktop application business logic

### Decomposition Strategy
1. **Database per Service**: Current H2 database could be split per domain
2. **API Versioning**: Servlet-based APIs would need versioning strategy
3. **Stateless Design**: Math APIs demonstrate stateless patterns; Auth APIs need refactoring
4. **Transaction Boundaries**: Library operations have clear transaction boundaries
5. **Communication Patterns**: Consider REST vs. messaging between services
6. **Testing Strategy**: Comprehensive test infrastructure supports microservice testing
7. **Configuration Management**: Externalize configuration for each service

### Migration Considerations
- **Gradual Decomposition**: Extract one domain at a time
- **API Gateway**: Needed for routing and aggregation
- **Service Discovery**: Required for dynamic service location
- **Distributed Tracing**: Essential for debugging across services
- **Circuit Breakers**: Needed for fault tolerance
- **Data Consistency**: Eventual consistency patterns for loan operations

This architecture provides a solid foundation for decomposition into focused microservices with clear separation of concerns, well-defined boundaries, and comprehensive testing support. The monolithic structure already demonstrates domain separation that aligns well with microservice principles.
